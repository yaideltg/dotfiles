# CSS Motion & Rendering Performance: Transitions, Transforms, Animations

Deep-dive reference distilled from *CSS in Depth* chapters 14–16. Load this file when adding hover/state transitions, building keyframe animations, working with 2D/3D transforms, or diagnosing janky/slow animation performance.

- `transition-property` (which properties; `all` = any that change), `transition-duration` (time, unit required — `0` alone is invalid for time values, must be `0s`/`0ms`), `transition-timing-function`, `transition-delay` — shorthand order: `transition: property duration timing-function delay;`. Multiple independent transitions: comma-separate full groups (`transition: border-radius 0.3s linear, background-color 0.6s ease;`) or use comma-separated lists in each longhand.
- Put the `transition` declaration on the BASE/default selector (not inside `:hover`/`.is-open` etc.) so it governs transitioning both INTO and OUT OF the changed state — a transition rule only present on the modifier state won't apply on the way back out.
- A transitioned property doesn't need an explicit starting value stated — e.g. transitioning `border-radius` still animates smoothly from an implicit 0 even if the base rule never declared `border-radius: 0`.
- Timing-function keywords (based on Bézier curves): `linear` (constant rate), `ease-in` (slow start, accelerates — fits system/automatic changes, e.g. content finishing loading, so it draws the eye before speeding to completion), `ease-out` (fast start, decelerates — fits user-initiated changes like clicks/hovers, so the response feels instant then settles), `ease`/`ease-in-out` for gentler default motion. Custom curves via `cubic-bezier(x1,y1,x2,y2)` (best tuned visually in DevTools' curve editor, then copy the resulting value) for finer control or bounce-like effects.
- `steps(N, start|end)` timing function moves the value in N discrete jumps rather than smoothly — `end` (default) applies each jump at the END of its step interval, `start` at the beginning.
- Recommended transition durations: keep most UI transitions (hover states, small fades) in the 200–500ms range, often nearer 100-300ms — longer durations start to feel like the page is "slow" to users, especially for frequently-repeated interactions (hovering many links). Temporarily slow a transition to 2-3s while tuning it in DevTools, then restore it to its real short duration before shipping.
- NOT ALL PROPERTIES CAN BE ANIMATED: only properties with a continuous value type (length, number, color, calc()) interpolate smoothly; properties with purely discrete/keyword values (`display`, `url()`-based values) cannot transition — the browser just flips instantly regardless of any transition rule applied to them. Check MDN's "Animation type" field for a property before relying on it to transition. This is exactly why you can't transition `display:none ↔ display:block` for a fade effect — use `opacity` (continuous, 0–1) instead.
- Classic fade-in/out + fully-remove-from-interaction pattern: don't rely on `opacity:0` alone to "hide" something — a 0-opacity element is invisible but STILL occupies space and STILL intercepts clicks. Combine with `visibility` (which IS transitionable, unlike `display`, and DOES remove interactivity/clickability while still occupying layout space) using a deliberately staggered transition-delay: on the CLOSE transition, delay the `visibility:hidden` switch until AFTER the opacity fade completes (`transition: opacity 0.2s linear, visibility 0s linear 0.2s;`), so the fade plays fully before the element stops intercepting clicks; on the OPEN transition, set `transition-delay: 0s` for visibility so it becomes interactive/visible immediately while opacity fades in.
- Transitioning to/from `height: auto` doesn't work directly — a browser can't interpolate between a fixed length and the keyword `auto` (the target value isn't knowable as a number ahead of time). Workaround requires JS: read the natural height via `element.scrollHeight` once, then explicitly set that pixel value as the CSS height (which CAN transition smoothly to/from `0`) instead of ever using `auto` in the transitioning rule. Note `scrollHeight` reads as `0` if the element is `display:none` — temporarily flip to `display:block`, measure, then revert if needed.
- General principle: let CSS handle as much of a transition/animation's actual interpolation as possible (it's more optimized/performant, and gives easing "for free") rather than reimplementing continuous motion by hand in JS — reserve JS for the parts CSS genuinely cannot do alone (toggling a class, or measuring/injecting a value like scrollHeight CSS has no way to know).
- The JS `transitionend` event lets you run followup code exactly when a CSS transition finishes (e.g. removing an element from the DOM only after its fade-out completes).

- Four transform categories: `rotate(deg)`, `translate(x,y)` (like relative positioning but far more performant), `scale(factor)`, `skew(deg)`. Transforms CANNOT be applied to inline elements (`<span>`, `<a>`) — change to `inline-block`, or make it a flex/grid item via its parent, first.
- `transform-origin` (default: center of the element) sets the pivot/anchor point for rotate/scale/skew (translate ignores it — the whole element just moves). Accepts keywords (`top left`, `right bottom`) or percentages/lengths measured from the element's own top-left corner.
- Multiple space-separated transform functions apply right-to-left order-of-operations (e.g. `transform: rotate(15deg) translate(20px,0)` translates FIRST then rotates — the translate axis then gets skewed by the rotation, making `translate` feel diagonal). If you want intuitive left/right-up/down translate behavior alongside a rotation, put `translate()` FIRST in the value list (it's applied last).
- SCALE AN IMAGE/ICON VIA TRANSFORM, NOT VIA WIDTH/HEIGHT, for a hover-grow effect — changing width/height triggers layout recalculation (can shift sibling elements), while `transform: scale()` only affects paint/composite and never disturbs surrounding document flow.
- Prefer SVG over sprite sheets or icon fonts for iconography: scales cleanly at any size (pairs perfectly with `transform:scale()` hover effects — no pixelation), can be inlined directly in HTML for CSS-controllable fill/stroke colors, and is generally smaller/more performant than raster icon formats.
- Staggering a repeated transition across sibling items (`:nth-child(2)`, `:nth-child(3)`... each with a slightly longer `transition-delay`, e.g. 0.1s increments) produces a natural "wave/cascade" feel instead of everything moving in lockstep — a small, cheap way to make a UI feel more polished. Downside: this only covers however many nth-child rules you write, so pad a couple extra beyond your current content count as a safety margin, or use a preprocessor loop to generate more.
- Combine `:hover` on a PARENT with `:focus` on the actual interactive child (e.g. `.nav-links:hover .label` AND `.nav-links a:focus > .label`) so mouse users get the group hover reveal while keyboard users tabbing through individual links still get the same reveal per-item — don't rely on `:hover` alone for anything that should also work via keyboard navigation.
- PERFORMANCE — THE RENDERING PIPELINE (layout → paint → composite): changing width/height/top/left/etc. forces LAYOUT to be recomputed (expensive — can cascade to recalculating position/size of many other elements = "reflow"); changing most visual properties (background-color, border, shadow) forces a repaint but not a re-layout (cheaper); changing ONLY `transform` and `opacity` can often skip both layout AND (main-thread) paint — the browser can promote the element to its own compositor layer and hand it to the GPU, updating it independently of the rest of the page.
- RULE OF THUMB: for anything transitioned or animated, prefer animating `transform` and `opacity` almost exclusively — they are dramatically cheaper than animating `left`/`top`/`width`/`height`/margins, especially noticeable with many simultaneously-animating or visually complex elements, and matters most because animations must recompute the frame ~60 times/second to look smooth. Reach for layout-triggering properties in an animation only when there is truly no transform/opacity-based alternative.
- `will-change: transform` (or the specific property you'll animate) is a hint that lets the browser pre-promote an element to its own layer ahead of time — use it reactively, only after observing actual jank/flicker, verify it helps with real before/after testing, and don't sprinkle it everywhere by default (extra layers cost memory). Reference: csstriggers.com lists exactly which CSS properties trigger layout/paint/composite.
- 3D transforms: `translateZ()` moves an element toward/away from the viewer; `rotateX()` (pitch, tips forward/back), `rotateY()` (yaw, turns left/right), `rotateZ()` (aliases plain `rotate()`, spins in the page plane).
- `perspective` is required for 3D transforms to look three-dimensional at all — without it, rotated elements just look horizontally squashed, not "receding into depth." Smaller perspective values (camera closer) = stronger/more exaggerated 3D effect; larger values = subtler. Two ways to apply it: the `perspective()` transform FUNCTION on an individual element (that element gets its own private vanishing point — as if separately photographed), or the `perspective` PROPERTY on a shared ancestor/container (all descendant 3D-transformed children share one common vanishing point — as if photographed together in one scene, generally what you want for multiple related elements like a row of cards).
- `perspective-origin` repositions the implied "camera" (default: centered) — e.g. `left bottom` shifts the vanishing point, exaggerating distortion toward one side.
- `backface-visibility: hidden` hides an element when a 3D rotation has turned it more than 90° away from the viewer (its "back" would otherwise show as a mirror image) — the classic building block for a flip-card effect (two faces back-to-back, rotate the shared container).
- `transform-style: preserve-3d` on a parent is needed when you rotate a CONTAINER whose children already have their own 3D transforms — without it, the browser flattens the children into one 2D "photo" first and then rotates that flat image (destroying the depth illusion); with it, the whole nested 3D scene rotates coherently together. Not supported in any version of IE.

- Two-part syntax: `@keyframes name { 0% {...} 50% {...} 100% {...} }` defines the animation; `animation: name duration timing-function iteration-count;` shorthand applies it to an element. Percentages mark WHEN in the timeline each keyframe's declared values should be reached — omit a property in some keyframes and it's simply interpolated smoothly across the surrounding keyframes that DO specify it (doesn't need to appear in every keyframe).
- `animation-iteration-count`: an integer, or `infinite` for endless looping (e.g. a loading spinner). If an animation repeats, make sure the 100% keyframe's values match the 0% keyframe's (or design intentionally otherwise) — mismatched end/start values cause a visible "snap" at each loop boundary.
- CASCADE PRIORITY: while an animation is actively running, its keyframe declarations OUTRANK ordinary author-stylesheet declarations on that element/property, REGARDLESS of selector specificity — animations act as an even-higher-priority "origin" than normal author CSS. After the animation ends (and with no fill-mode holding values), the element's styling reverts to whatever the normal cascade would otherwise apply.
- Mobile browser support historically needed `-webkit-` prefixes on both `animation` and `@keyframes` — handle via Autoprefixer, don't hand-duplicate.
- 3D fly-in effects: combine `perspective` (on a shared container) with `translateZ()` + `rotateY()` keyframes and an `opacity` fade — e.g. start translated far back and rotated ~90°, opacity 0; mostly resolve position/opacity by a middle keyframe; finish at translateZ(0) rotateY(0) opacity 1. Gives a strong "flying toward the viewer" effect using only compositor-friendly properties (transform + opacity — cheap to animate, see motion/performance notes).
- STAGGERING: apply slightly increasing `animation-delay` per sibling (via `:nth-child()`) exactly as with transition-delay, to make a group "fly in" one after another instead of simultaneously.
- ANIMATION-DELAY GOTCHA: before a delayed/staggered animation starts playing, the element sits in its NORMAL (non-keyframe) styled state — visible in its final position — then suddenly jumps to the 0% keyframe values right as the animation begins, producing an unwanted flash/jump. Fix with `animation-fill-mode`:
  - `backwards`: applies the FIRST keyframe's (0%) values to the element even before the animation starts/during any delay — eliminates the pre-animation flash for entrance effects.
  - `forwards`: keeps the LAST keyframe's (100%) values applied after the animation ends (instead of reverting to the element's normal declared styles) — needed if the animation's end state should persist and differs from the element's base CSS.
  - `both`: applies both behaviors (backwards before start, forwards after end).
  - Default `none` applies keyframe values only while actually running.
- MEANINGFUL ANIMATION, not just decoration: animation should communicate state/feedback, not merely add flourish. Two concrete, reusable patterns:
  - LOADING SPINNER: absolutely-positioned pseudo-element with a partial border (e.g. `border-top` colored, other sides transparent or same-as-background) shaped into a circle via `border-radius:50%`, animated with `animation: spin 0.5s linear infinite; @keyframes spin { to { transform: rotate(360deg); } }`. Toggle a `.is-loading` state class via JS on user action (form submit) — hide the normal label (`color:transparent`) while the spinner pseudo-element shows.
  - ATTENTION/REMINDER SHAKE: a keyframe animation rapidly alternating `translateX()` left/right (reusing identical keyframe blocks at multiple percentages via comma-separated selectors, e.g. `10%, 30%, 50%, 70% { transform: translateX(-0.4em); }`), tapering the amplitude down toward the end for a natural "settling" feel. Trigger via a debounced JS timer (e.g. add a `.shake` class if the user pauses typing for 1s) and remove the class again on the JS `animationend` event so it can replay next time.
- Prefer toggling a CSS class from JS to start/stop/repeat an animation over any hand-rolled JS-driven animation loop — CSS handles the interpolation more efficiently and gives easing behavior for free; JS's job is just deciding WHEN to flip the class (and cleaning it up via `animationend`).
- Repeated near-identical `:nth-child` blocks (e.g. staggered delays) are exactly the kind of repetition a preprocessor loop (Sass `@for`) can generate automatically instead of hand-typing each one — worth using if the codebase already has Sass/Less.
- Curated pre-built keyframe animation library for inspiration/reuse: animista.net.
