# CSS Architecture: Modular CSS, Naming, Pattern Libraries

Deep-dive reference distilled from *CSS in Depth* chapters 9–10. Load this file when organizing a stylesheet for a multi-page/multi-component project, naming classes, deciding between BEM/OOCSS/SMACSS conventions, or setting up a component library / design-system workflow.

## Contents
1. Modular CSS: encapsulation, BEM-style naming, single responsibility, utility classes
2. Pattern libraries: documentation, CSS-first workflow, treating CSS as a versioned API

---

- Modular CSS = encapsulation applied to CSS: break the page into independent, reusable modules (components) so a change in one never has unintended side effects elsewhere.
- Stylesheet structure, in order: (1) BASE rules — generic element/tag-only selectors (body, headings, links, form resets), no classes or IDs, rarely touched once set; consider adding normalize.css as a foundation; (2) MODULE rules — the bulk of the stylesheet, one module at a time; (3) UTILITY classes — small single-purpose overrides, kept at the very end/bottom so they win the cascade.
- CORE RULE — a module's selector must be ONLY its own class name, nothing else: `.message { }` not `#sidebar .message { }`. Restricting a module to a particular ancestor context (a "context-dependent selector") is explicitly forbidden — it makes the module non-reusable, creates ambiguity about where to put the code, ratchets up specificity over time, and couples CSS to one specific HTML structure. If a module needs to look different in a specific place, create a MODIFIER class instead (see below), never reach into it from outside via a descendant selector.
- MODIFIERS: a class that starts with the module name plus `--` (double-hyphen, from BEM) to layer a variation, e.g. `.message--error`, `.button--success`, `.button--large`. Modifier rules only override what changes (colors, size) — not the whole module. Apply both classes together in HTML: `<div class="message message--error">`.
- SUB-ELEMENTS: for a module with multiple internal pieces, name them `module__subelement` (double-underscore, BEM), e.g. `.media__image`, `.media__body` — the name alone makes uniqueness/scope obvious without needing a descendant selector chain. A generic-but-clearly-scoped tag selector inside the module (e.g. `.media__body > h4` for the title, `.menu > li` for items) is fine and can save boilerplate classes — but avoid targeting truly generic tags like bare `div`/`span` inside a module (you may need a second unstyled span later and then have to hunt down every usage to add a class).
- SINGLE RESPONSIBILITY PRINCIPLE for modules: if describing a module's job requires "and" (e.g. "toggles a menu AND presents stacked items"), it's probably two modules. Split them: e.g. a `.dropdown` module (toggle + show/hide only) that CONTAINS a separate, independent `.menu` module (list styling only) — the dropdown has no knowledge of menu internals and vice versa, so either can be reused or swapped independently.
- Keep all code for one module together/contiguous in the stylesheet (or, with a preprocessor, in its own file, imported via a manifest like `@import 'message'; @import 'button';` — makes editing and locating a module trivial).
- STATE CLASSES: a special class toggled by JS to reflect dynamic state, conventionally prefixed `is-` or `has-` (e.g. `.is-open`, `.is-loading`, `.has-error`). JS should only add/remove this class name — never set styles directly via JS/inline style — leaving 100% of the visual logic in CSS. Define state-class rules right alongside the rest of that module's CSS.
- When a module itself needs positioning (relative/absolute), keep the positioned parent and its positioned children WITHIN the same module's rules, so it behaves consistently no matter what larger, possibly-also-positioned container it's dropped into.
- NAMING modules: name by what the module conceptually IS/represents, never by its current visual appearance (`gray-box-with-image` breaks the moment the design changes color) and never by its current content/context (`running-tip` breaks if reused for something else) — `media` works because it's abstract and durable. Apply the same principle to modifier names: prefer semantic names (`button--danger`, `button--success`) over color/visual names (`button--red`) or overly precise ones (`button--20px`) so the code doesn't lie after a redesign; relative modifiers like `--large`/`--small` are an acceptable middle ground since they only need to stay relatively true.
- UTILITY CLASSES: tiny, laser-focused, usually single-declaration helper classes (e.g. `.text-center`, `.float-left`, `.hidden`, a shared `.clearfix`) kept together at the end of the stylesheet. This is explicitly the ONE place `!important` is acceptable/expected — a utility class's entire purpose is to reliably win regardless of where it's applied. Don't overdo it — most projects need only a handful of these.
- Named CSS methodologies worth knowing (in order of increasing structure/rigidity): OOCSS (Object-Oriented CSS, Nicole Sullivan), SMACSS (Scalable and Modular Architecture for CSS, Jonathan Snook — adds a distinct "layout rules" category for page regions/grid), BEM (Block-Element-Modifier, the double-hyphen/double-underscore naming convention used throughout this chapter), ITCSS (Inverted Triangle CSS, Harry Roberts — divides a stylesheet into ~7 specificity-ordered layers). Pick one (or blend), and get team agreement — consistency matters more than which one.
- CSS-in-JS (Aphrodite, Styled Components, CSS Modules) is an alternative to class-naming-discipline for JS-framework-rendered apps (e.g. React) — generates guaranteed-unique class names or inlines styles via JS, trading some flexibility/tooling lock-in for automatic scoping.

- A pattern library (aka style guide) is a standalone set of documentation pages (not shipped to production) inventorying every module in the stylesheet, generated from special comment blocks in the CSS (tools: KSS, or others — "style guide generator" is the search term). Each entry shows: a title, a markdown description (module purpose, any JS requirements, dependencies on other modules), a rendered live example, the example HTML/markup to copy, and (for modules with variants) the list of modifier classes.
- Distinguish "pattern library" (technical/reusability documentation) from "style guide" (adds opinionated brand/usage direction, e.g. "don't use red buttons for X") — same tool can serve either purpose.
- CSS FIRST workflow (a deliberate inversion of the usual "write HTML then style it" order):
  1. Start from a sketch/mockup for the page.
  2. Check the pattern library first; assemble the page purely from EXISTING modules, outside-in (page containers/layout first, then inner components) — write zero new CSS if possible.
  3. Only when something genuinely doesn't exist yet, build (and document) the new module or modifier INSIDE the pattern library, in isolation, before touching the page.
  4. Only then wire the new module into the actual page's HTML.
  Benefits: forces reuse over duplicate/near-duplicate styles (consistent UI); lets a developer focus on a module in isolation so the resulting solution tends to be more general/reusable; lets CSS-specialist and CSS-non-specialist teammates divide labor cleanly (hand off a link to a pattern-library entry); documentation is always current because it lives with the code being tested/exercised as you edit.
- THE API MINDSET: think of each module's class names + required DOM structure as a versioned API contract between your CSS and any HTML that uses it. HTML content inside a module is free to change; the CSS internals are free to change (e.g. rewriting floats to flexbox) — AS LONG AS the documented class-name/structure contract still holds. This is what makes editing/refactoring CSS on a large site safe rather than terrifying.
- Safe-edit technique for evolving a module: add the NEW use-case's example markup alongside the OLD one in the pattern-library documentation comment (don't remove the old example), confirm the old one currently renders fine, then edit the CSS until both examples work correctly — the pattern library becomes a visual regression check/backstop for that module before you ever touch the live site.
- When a change would genuinely require breaking the existing API (can't be done backward-compatibly), prefer deprecating the old module (mark it in the docs) and creating a NEW module for the new behavior, rather than mass-editing all its call-sites at once — lets consumers migrate gradually while old usages keep working unmodified.
- Version the CSS itself with semver (major.minor.patch): patch = non-breaking bug fixes; minor = new module/feature or marking something deprecated (no break); major = actual breaking API changes or deleting deprecated modules (or a full visual redesign even without a breaking API). This lets consumers of the stylesheet pin/opt into upgrades deliberately instead of being broken by a silent change.
- On off-the-shelf frameworks (Bootstrap, Foundation, Pure, etc.): don't just link the framework's whole compiled CSS file as-is on top of your own — you'll end up writing endless override/augmentation rules against it, bloating and complicating the page. Instead, treat the framework as a source of individual modules: copy in only the specific pieces you actually need (license permitting) directly into your own stylesheet/pattern library, where you can edit them freely as your own code. Mentally, "build your own framework" (a project-specific pattern library) rather than consume someone else's wholesale — a framework is itself just a general-purpose pattern library, and yours can be more precisely tailored to your project's brand/needs.
- Cultural payoff: without modular architecture + a pattern library, CSS tends to become "additive only" — developers, afraid of unknown side effects, only ever append new overriding rules (never edit/delete), and specificity/size spiral upward forever. A documented, versioned, modular system is what makes deleting and refactoring CSS safe again.
