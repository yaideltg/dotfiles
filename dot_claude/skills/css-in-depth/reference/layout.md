# CSS Layout: Floats, Flexbox, Grid, Positioning, Responsive Design

Deep-dive reference distilled from *CSS in Depth* chapters 4–8. Load this file when building page layouts, choosing between flexbox/grid/floats, debugging positioning/stacking, or implementing responsive breakpoints.

- Floats' ORIGINAL purpose: pull an element (image) to one side so surrounding text wraps around it (magazine/newspaper-style layout) — using them for full PAGE layout was always a repurposing/hack, not their design intent, but was the only option for ~2 decades before flexbox/grid existed.
- A floated element leaves normal document flow; siblings' text wraps around the space it occupies. Floating multiple elements the same direction stacks them side by side (until they don't fit, then they wrap to a new line).
- CONTAINER COLLAPSE: a container whose only children are floated will collapse to zero height (floats contribute no height to their parent) — this is why a floated layout's background/border often fails to wrap its content.
- THE CLEARFIX pattern fixes container collapse without extra markup, via a pseudo-element:
  ```css
  .clearfix::after { content: " "; display: block; clear: both; }
  ```
  Apply the clearfix class to the CONTAINER that holds the floats (a common mistake is applying it to the floated elements themselves, or to a later sibling). A more robust version also uses `::before { content:" "; display:table; }` to additionally prevent margin-collapsing through the container (table display implicitly creates a table-cell, and margins don't collapse through table-cells).
- FLOAT "CATCHING": when floating a sequence of same-direction elements of inconsistent height (e.g. a grid of boxes), a later float can snag against the bottom corner of an earlier, taller box instead of dropping to a full new row — even a 1px height difference can trigger this. Fix: force each "first item of a row" to clear the row above, typically via `:nth-child(An+B)` selectors (e.g. `:nth-child(odd) { clear: left; }` for a 2-per-row layout) — but this only works when you know a fixed number of items per row; if the count varies by viewport, switch to flexbox/grid instead.
- BLOCK FORMATTING CONTEXT (BFC): an isolated rendering region that (1) contains all floats within it, (2) contains top/bottom margins within it (no collapsing out), and (3) does not let outside floats overlap into it. Trigger a new BFC via: `float` (anything but none), `overflow` (anything but visible — `auto`/`hidden` are the common non-disruptive choices), `display: inline-block/table-cell/flex/grid` (and their inline-* variants), or `position: absolute/fixed`. Media-object pattern: give the TEXT-BODY sibling of a floated image `overflow:auto` (or similar) so it establishes its own BFC and its text doesn't wrap under/around the float — its box will sit flush next to the float instead.
- DOUBLE CONTAINER PATTERN: an outer container (often `<body>`, full width) wraps an inner container with `max-width: Npx; margin: 0 auto;` — centers content while letting the outer element's background bleed to the viewport edges. Using `max-width` instead of `width` lets the inner container shrink gracefully on narrow viewports instead of forcing horizontal scroll.
- MEDIA OBJECT PATTERN (image + text body side-by-side, foundational UI pattern — also achievable with flexbox/grid): float the image left with a right margin for the gutter; give the body `overflow:auto` to create its own BFC so it doesn't wrap under the image.
- Hand-rolled GRID SYSTEM (12-column convention — divisible by 2/3/4/6, giving flexible split options): a `.row` wrapper (clearfix + negative left/right margin equal to half the gutter, to compensate for column padding and keep outer edges aligned with the rest of the page) containing `.column-N` children floated left with `width: N/12 * 100%` and left/right padding of half the gutter each (attribute selector `[class*="column-"]` is a handy way to apply the shared float/padding rules to every column class at once, but be aware it also matches any unrelated class containing that substring — treat "column" as a reserved naming prefix once you do this). Precompute widths to several decimal places to avoid visible rounding gaps.
- Practical modern take: floats and hand-rolled grid systems remain useful knowledge for maintaining legacy code, supporting old browsers, or markup you can't fully control (floats need less wrapper markup) — but for new work, flexbox/grid layout (ch5/ch6) are simpler and more predictable, and are where new grid systems should be built today.

- `display: flex` on a parent turns it into a flex container; direct children become flex items laid out along the MAIN axis (default row, left→right); CROSS axis is perpendicular. `display: inline-flex` behaves like inline-block for the container itself.
- Use `flex-direction: column` to stack items top-to-bottom (also `row-reverse`, `column-reverse`) — changes which axis is "main" so flex/grow/shrink then act on height instead of width.
- Vendor prefixes: old Safari needed `-webkit-flex`, old IE10 needed the old spec (`-ms-flexbox` + old property names) — in practice, always run production CSS through Autoprefixer instead of hand-writing prefixes.
- Apply padding to the actual clickable `<a>` inside a `<li>` nav item, not the `<li>` itself, and set that `<a>` to `display:block` so its own padding/box contributes to the flex item's size (an inline link's height comes from line-height only, not padding).
- Spacing flex items: use margin (e.g. `li + li { margin-left: 1.5em }`, a flex-adapted lobotomized-owl pattern) for uneven/one-off gaps. `margin: auto` on a flex item consumes ALL remaining free space on that side — classic trick to push one nav item (e.g. "About") to the far end without extra wrapper markup.
- The `flex` shorthand = `flex-grow flex-shrink flex-basis`. UNLIKE most shorthands, omitted parts do NOT reset to spec-initial values — `flex: 2` fills in flex-shrink:1 and flex-basis:0% (the commonly wanted defaults), not the individual properties' real initial values. Always prefer the shorthand over setting the three individually.
- `flex-basis`: starting main-size before grow/shrink is applied; default `auto` looks at the element's own `width`/`height` or its content; setting a basis other than `auto` makes an explicit `width` on that item irrelevant.
- `flex-grow`: non-negative integer "weight" for how leftover space (container width minus all items' basis+margins) is distributed; 0 = don't grow. Two items with grow 2 and 1 split the remainder 2:1.
- `flex-shrink`: same weighting but for how much to shrink each item when the combined basis overflows the container; 0 = never shrink (can overflow).
- Two equivalent ways to build proportional columns: (a) `flex:2` / `flex:1` (basis 0%, so 100% of width is "remainder" split by ratio) or (b) `flex: 66.67%` / `flex: 33.33%` (basis = actual percentage, flex-shrink absorbs any gutter overflow) — note padding differences between items can make these two methods diverge slightly; use the percentage-basis method when precise widths matter and paddings aren't equal.
- Practical flex-size patterns: `flex: none` = natural size (no grow/shrink); `flex: 0 0 300px` = fixed width, add `max-width` if content could force it wider; `flex: 1` on a middle column = fluid center, e.g. the classic "Holy Grail" 3-column layout (`flex:0 0 200px` / `flex:1` / `flex:0 0 200px`) — trivial with flexbox, historically painful with floats.
- Nested flexbox pattern for "sidebar with two stacked tiles that must equal-height match a main column": give sidebar `flex:1; display:flex; flex-direction:column;` (it's both a flex item of the outer row AND a flex container for its own column), then give each inner tile `flex:1` so they stretch to fill whatever height the outer row establishes. In a vertical (column) flex container, height is still determined by content unless an ancestor constrains it — flex-grow/shrink on vertical items only kicks in if something above forces a fixed height.
- `justify-content` = main-axis distribution (flex-start/end/center/space-between/space-around); has NO effect if any item has flex-grow>0 or an auto margin on the main axis (they already consumed the free space).
- `align-items` = cross-axis alignment (default `stretch`, so flexbox gives equal-height columns automatically); other values: flex-start/end/center/baseline. Mnemonic to avoid confusing the two: "justify" = horizontal text spreading; "align" = vertical, like `vertical-align`.
- `align-self` on an individual item overrides the container's `align-items` for just that item (ignored if that item has an auto margin on the cross axis).
- `order` (integer, default 0) visually reorders items regardless of source order — WARNING: keyboard Tab-navigation and screen readers still follow DOM/source order, so large visual/DOM order mismatches hurt accessibility.
- Don't reach for flexbox everywhere by default — trust normal document flow for content that doesn't need it (e.g. paragraphs of body text); use flexbox intentionally for actual layout/alignment problems.
- KNOWN ISSUE: flexbox row layouts can cause a visible "reflow flash" on slow connections — the browser renders items with whatever content has loaded so far, then reflows/resizes once the rest arrives, since flex sizing depends on all siblings' content. This is specific to multi-column ROW layouts, not COLUMN (stacked) ones. For a full-page layout skeleton where this matters, grid layout is a better choice than flexbox (per Jake Archibald).
- Check "Flexbugs" (github.com/philipwalton/flexbugs) for known cross-browser flexbox quirks and documented workarounds before assuming your own code is wrong.
- Real inputs need `width:100%` explicitly if you want them to fill their container — an `<input>`'s width is governed by its `size` attribute, not normal block-level auto-fill behavior, even with `display:block`.
- `cursor: pointer` on a non-`<a>` clickable element (e.g. a styled button/div acting like a link) signals clickability to the user.

- `display: grid` on parent → grid container; direct children → grid items (must be DIRECT children — no deep-nesting like flexbox's tree, so a grid layout often requires "flattening" HTML compared to a nested-flexbox version of the same design).
- Define tracks with `grid-template-columns`/`grid-template-rows` using `fr` (fraction) units (like flex-grow), fixed units (px/em), `%`, or mixes (`300px 1fr` = fixed sidebar + fluid remainder). `repeat(N, value)` shorthand avoids repeating identical track definitions; `repeat(3, 2fr 1fr)` repeats a whole PATTERN (6 tracks total), and repeat() can sit inside a longer list: `1fr repeat(3,3fr) 1fr`.
- `grid-gap` (now `gap`) sets gutter between tracks; two values = row-gap column-gap.
- Grid vocabulary: grid LINE (the numbered dividers, start at 1 top-left, negative numbers count from bottom-right of the EXPLICIT grid regardless of later-added implicit tracks), grid TRACK (a row or column), grid CELL (single intersection), grid AREA (rectangle of 1+ cells).
- Place items with `grid-column`/`grid-row` shorthand as `start / end` line numbers (e.g. `grid-column: 1 / 3`), or `grid-row: span 1` to span N tracks from an auto-placed start (lets the placement algorithm pick position while you only fix the span).
- Named grid lines: `grid-template-columns: [start] 2fr [center] 1fr [end];` then reference by name (`grid-column: start / center`). A line can have multiple names (`[left-end right-start]`), and pairing `name-start`/`name-end` on a track definition auto-creates a usable named AREA you can reference with just `name` in grid-column. Repeating the same bracket name across `repeat()` iterations is valid and useful for "nth set of columns" addressing (`grid-column: col 2 / span 2`).
- Named grid AREAS (`grid-template-areas`) — an "ASCII art" string per row assigning each cell a name (`"title title" "nav nav" "main aside1" "main aside2"`), then each item gets `grid-area: <name>`. A named area MUST form a solid rectangle (no L/U shapes). Use `.` for a deliberately empty cell. This syntax is often the most readable for one-off page layouts because you can literally see the shape.
- THE flexbox-vs-grid decision: flexbox is one-dimensional (content-driven — items size themselves, sizing flows content→layout) and best for rows/columns of similar elements (e.g. nav bar); grid is two-dimensional (layout-driven — you define structure first, then place content into it) and best whenever items in one row must align with items in another row/column (e.g. whole-page skeleton). In practice: grid for the high-level page layout, flexbox for the internals of individual regions (nav bar, price display) — they're complementary, not competing.
- Explicit vs implicit grid: tracks you declare via grid-template-* are "explicit"; placing an item outside them auto-generates "implicit" tracks (default size `auto`, override with `grid-auto-columns`/`grid-auto-rows`, e.g. `1fr` for equal-height implicit rows).
- Responsive auto-count grid (no media queries needed): `grid-template-columns: repeat(auto-fill, minmax(200px, 1fr));` — auto-fill packs as many ≥200px columns as fit the container, expanding/collapsing count as viewport resizes. `auto-fit` behaves the same but STRETCHES existing tracks to fill leftover space instead of leaving empty tracks — prefer `auto-fit` unless you specifically want to preserve empty placeholder tracks.
- `grid-auto-flow` controls the item-placement algorithm: default `row` fills row-by-row; `column` fills column-by-column; add `dense` (e.g. `grid-auto-flow: column dense`) to let SMALLER items backfill visual gaps left by larger spanning items — but this can reorder items away from source/DOM order, hurting keyboard-tab and screen-reader navigation (same caution as flex `order`).
- To make a grid item's own content (e.g. an `<img>`) actually fill its stretched grid cell without distortion: make the item itself `display:flex; flex-direction:column;`, give the inner element `flex:1` to stretch, and pair with `object-fit: cover` (crop, no distortion, fills box) or `object-fit: contain` (letterbox, no cropping, no distortion) instead of the default `fill` (which stretches/distorts).
- Progressive enhancement pattern for a new-ish layout feature: write base/fallback styles (e.g. inline-block layout) OUTSIDE any feature query so all browsers get them, then wrap the enhanced grid styles in `@supports (display: grid) { ... }` and override/replace the fallback declarations inside that block. `@supports not(...)`, `... or (...)`, `... and (...)` combine conditions. IE ignores `@supports` entirely (falls through to the fallback, which is generally fine/intended).
- Grid alignment properties mirror flexbox but with a THIRD tier: `justify-items`/`align-items` (on the container, aligns each item's content WITHIN its own grid area — grid's extra concept vs flexbox), `justify-self`/`align-self` (per-item override), `justify-content`/`align-content` (positions the whole set of tracks within the container when total track size < container size — supports `space-evenly`, not available in flexbox).
- Reference: gridbyexample.com (Rachel Andrew) for exhaustive worked examples of every grid alignment/placement property.

- `position` values: `static` (default, "not positioned," normal flow) → `relative`, `absolute`, `fixed`, `sticky` are all "positioned." Positioning REMOVES an element from normal flow (except relative, see below) so you become responsible for what flow used to handle for you (avoiding overflow/overlap).
- FIXED: positions relative to the viewport itself, unaffected by scrolling. Specifying opposite sides (e.g. top+bottom, or left+right) both implicitly sets the element's size (distance between them) — omit one side (e.g. no `bottom`) to let height/width size naturally from content instead. A fixed element is fully removed from flow, so other content flows underneath/behind it — compensate with a margin on the content container matching the fixed element's size (e.g. `margin-right:20%` for a fixed right sidebar) to prevent overlap.
- Modal dialog pattern: a full-viewport `position:fixed` "backdrop" (all 4 sides = 0, `background: rgba(0,0,0,0.5)` for a translucent dark overlay) plus a separately `position:fixed` centered "body" box with its own `overflow:auto` so long content scrolls inside the modal, not the page.
- ABSOLUTE: positioned relative to the nearest POSITIONED ancestor (its "containing block") — walks up the DOM until it finds one; if none exists, falls back to the page's "initial containing block" (viewport-sized, anchored at page top). This is why "wrap the target in a `position:relative` parent with no visual effect" is the standard trick to scope an absolutely-positioned child.
- RELATIVE: shifting with top/right/bottom/left moves the element from its ORIGINAL spot but leaves a hole — sibling elements are NOT affected/reflowed (unlike absolute/fixed which fully exit flow). You can use top OR bottom (not both — bottom is ignored if both given), and left OR right (same rule); no implicit sizing like fixed/absolute. Relative positioning's most common real use is NOT to nudge things — it's to establish a containing block ("anchor") for an absolutely-positioned descendant, with zero visible effect by itself.
- Accessible icon-button trick: keep meaningful text in the HTML (e.g. "close") for screen readers, then visually hide it via `text-indent` pushing it out + `overflow:hidden` on the button, and inject a visual glyph via `::after { content: "\00D7"; }` (CSS content property needs the escaped unicode codepoint, not the HTML entity) positioned absolutely inside. Never delete meaningful text from markup just to show a symbol — CSS should only change how meaningful HTML content is presented.
- CSS-triangle trick: give a zero-size (no content, no width/height) pseudo-element a thick border; make 3 of the 4 border sides `transparent` and leave one colored — that one side renders as a solid triangle (e.g. `border: 0.3em solid; border-color: black transparent transparent;` = a downward-pointing triangle from the top border). Cheaper than a background image, no network request.
- STACKING ORDER without any positioning: later elements in source order paint over earlier ones. Once ANY element gets `position` other than static, ALL positioned elements paint IN FRONT of ALL non-positioned ones, regardless of source order; among positioned elements with no z-index, source order still decides who's on top.
- `z-index` only has effect on POSITIONED elements (static elements ignore it entirely). Setting a z-index (any value) on a positioned element creates a NEW STACKING CONTEXT rooted at that element: all its descendants are now painted as one atomic group relative to the rest of the page — a descendant's z-index, however high, can NEVER escape in front of something that's already stacked above its own ancestor's context. This is the classic "z-index: 99999 still doesn't work" bug — the fix is to find and raise the ANCESTOR stacking-context root, not the child.
- Other properties that ALSO create a new stacking context even without z-index: `opacity` < 1, `transform`, `filter` (and the root `<html>` always creates the top-level one).
- Stack order within one context, back to front: negative z-index positioned elements → normal static elements → z-index:auto positioned elements → positive z-index positioned elements.
- TIP: centralize all z-index values as named custom properties/variables in one place (e.g. `--z-nav-menu:200; --z-modal-body:410;`), spaced in increments of 10/100 so new layers can be inserted between existing ones later — prevents an escalating "z-index war" of arbitrary huge numbers.
- Practical fix for fixed-position elements (like modals) getting stuck in the wrong stacking context: move their markup to just before `</body>` so they aren't nested inside some other stacking-context-creating ancestor. This only works cleanly for `fixed` (position is independent of markup location); relative/absolute depend on their place in the DOM/flow so can't always be relocated this way.
- General caution: avoid positioning dozens of elements on a page — every one is a piece of manual layout math the browser's normal flow would otherwise handle for you, and stacking-context bugs compound in complexity. Prefer flow-based layout (flex/grid/floats) whenever it can achieve the same result; reserve position for genuine "stack elements in front of each other" needs (modals, tooltips, dropdowns).
- STICKY (`position: sticky` + an offset like `top: 1em`): hybrid of relative+fixed — scrolls normally until it would cross the given viewport threshold, then "locks" like fixed until its PARENT container's bottom edge scrolls past, at which point it resumes normal scrolling. Requires the parent to be taller than the sticky element itself, or there's no room to "stick." Good default pattern for a sidebar nav that should track scroll only within its own column. Needs `-webkit-` prefix for older Safari; use fixed/absolute as fallback for non-supporting browsers.
- Dropdown-menu pattern: relative-positioned wrapper containing a visible label + an absolutely-positioned hidden submenu (`display:none`), revealed via `.dropdown:hover .dropdown-menu { display:block }`. Caveat (accessibility): hover-only triggers don't work reliably on touchscreens and ignore keyboard Tab navigation / screen readers — real production dropdowns need JS-driven class toggling with proper focus handling, not pure `:hover`.

- Three pillars of responsive design: (1) mobile-first build order, (2) media queries (`@media`), (3) fluid (percentage/flex/grid-based) layout containers — never a fixed-desktop site scaled down.
- MOBILE FIRST means literally writing the mobile CSS as the unqualified base rules (no media query) and layering `min-width` media queries on top for progressively larger screens — not designing desktop-first and cramming it smaller. Same HTML serves all breakpoints; only CSS (and JS-toggled classes) differ. Content order in the HTML should generally put the most important content first (helps both mobile UX and accessibility/screen-reader/tab order), though exceptions are fine when justified (e.g. a hero banner near the top for visual impact even though it's not the "most important" content).
- Always include the viewport meta tag: `<meta name="viewport" content="width=device-width, initial-scale=1">` — without it mobile browsers render as if on a wide desktop viewport and then shrink, defeating all your media queries. Avoid adding `user-scalable=no` — blocking pinch-zoom actively harms users who need to zoom to read or tap accurately.
- Mobile touch targets: make clickable areas (menu links, buttons) generously padded — don't force users to zoom in to tap precisely.
- Hamburger menu pattern: absolutely-position the toggle button (pulled outside its container with a NEGATIVE top offset) inside a `position:relative` nav wrapper; toggle a class like `is-open` via JS `classList.toggle` (not inline styles) so a single compound selector (`.menu.is-open .menu-dropdown { display:block }`) controls visibility — keep the JS to one class toggle, let CSS do all the visual work. Caution (UX evidence, not just accessibility): hiding primary nav behind a hamburger has been shown to reduce user interaction with it — a deliberate design tradeoff to discuss with stakeholders, not a free win.
- Accessibility landmarks: screen-reader users jump between semantic regions (`<nav>`, `<main>`, `<aside>`, `<form>`) — put an interactive toggle INSIDE the `<nav>` it controls, not as a sibling, or screen-reader users who jump to nav find it apparently empty (a `display:none` submenu is skipped entirely by assistive tech).
- Media query basics: `@media (min-width: Xem) { ... }` — ALWAYS use ems for the breakpoint value, not px or rem: ems remain reliable across all major browsers even when the user has zoomed or changed their default font size (px/rem breakpoints are known to misbehave in Safari under those conditions). Combine conditions with `and` (both must hold) or comma (either can hold, i.e. logical OR).
- Order matters: put each breakpoint's overriding media query AFTER the base (mobile) rule for that selector in source order, so normal cascade/source-order lets it win at equal specificity — media queries don't change specificity themselves.
- Useful media features beyond width: `min-height`/`max-height`, `orientation: landscape|portrait`, `min-resolution`/`max-resolution` (retina detection — combine `(-webkit-min-device-pixel-ratio: 2), (min-resolution: 192dpi)` for cross-browser high-DPI targeting since Safari needs the old proprietary feature and IE/Opera Mini need `dpi` not `dppx`).
- `@media print { ... }` for print-specific styles — typically hide chrome/nav/footer via `display:none`, and force plain black text on no background (`* { color:black !important; background:none !important; }` inside the print block — one of the few legitimate places for `!important`, since print styles are a self-contained override layer with nothing further to conflict with).
- A `<link rel="stylesheet" media="(min-width:45em)" href="large.css">` media attribute organizes CSS into separate files for readability, but the browser downloads ALL linked stylesheets regardless of whether their media condition matches — this is a code-organization tool, not a network-bandwidth optimization.
- Breakpoint selection: don't target specific devices/models (screen sizes are far too numerous and always changing) — instead resize the browser and pick the point where YOUR design (esp. multi-column content) starts looking cramped or oddly spaced; that's your breakpoint. Multi-column sections are usually where the real breakpoints reveal themselves.
- Container queries (element-level, not viewport-level, responsive rules) did NOT exist yet in browsers at the time of this book (a known gap/wishlist item) — the workaround was fragile deeply-scoped descendant selectors. (Note: real container queries have since shipped in modern browsers — verify current support if relying on this.)
- Fluid layout rule of thumb: think in percentages / flex-grow+shrink / grid fr units for container and column widths, never fixed pixel container widths that force horizontal scrolling on narrow screens. An unstyled web page is responsive by default (block elements fill width, inline text wraps) — CSS is what breaks that if you're not careful, so preserve the natural fluid behavior as your baseline.
- Responsive tables (a persistently hard case): best fix is to restructure the DATA presentation for mobile (cards/tiles instead of a wide table) rather than force a real table narrower. If you must keep a real `<table>`, a fallback CSS hack under a `max-width` query: `display:block` on table/thead/tbody/tr/th/td (turns rows into stacked blocks), and hide (not remove) the header row by moving it off-screen with absolute positioning + huge negative offsets rather than `display:none`, preserving it for screen readers.
- Responsive images: (1) always compress/optimize images; (2) serve different resolutions per breakpoint for CSS `background-image` via matching media queries per breakpoint (small/medium/full-size files at increasing min-widths); (3) for `<img>` tags use the `srcset` attribute (`srcset="a.jpg 560w, b.jpg 800w, c.jpg 1280w"` plus a `src` fallback for non-supporting browsers) so the browser itself picks the right resolution — including accounting for device pixel density automatically; (4) ALWAYS add a global `img { max-width: 100%; }` safety net so images never overflow their container width in a fluid layout.
