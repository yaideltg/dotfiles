# CSS Visual Design: Backgrounds, Shadows, Color, Contrast, Spacing, Typography

Deep-dive reference distilled from *CSS in Depth* chapters 11–13. Load this file when implementing a visual design/mockup precisely, choosing colors, tuning spacing/line-height, working with gradients/shadows/blend-modes, or loading web fonts.

- `background` is shorthand for 8 sub-properties (image, position, size, repeat, origin, clip, attachment, color) — prefer setting individual longhand properties when using more than a couple, since the shorthand resets every omitted one to its initial value (same shorthand-gotcha as font/ch1).
- `background-attachment: fixed` (background stays put while content scrolls) can have real scroll-performance costs — use cautiously.
- `linear-gradient(angle, color1, color2, ...)`: angle can be a keyword (`to right`, `to bottom right`) or a unit — `deg` (0deg=up, clockwise), `turn` (0.25turn = 90deg), `rad`, `grad`. Extra color "stops" beyond 2 are evenly spaced by default, or can be pinned with explicit positions (`red 0%, white 50%, blue 100%`).
- Hard-edged color-stops (two stops at the SAME position) create instant stripes instead of smooth blends — e.g. `red 40%, white 40%, white 60%, blue 60%`. Combine with `repeating-linear-gradient()` for barber-pole/progress-bar stripe patterns (use fixed length units, not %, so the repeat unit size is well-defined).
- `radial-gradient()` defaults to an ellipse centered in the element, matching its aspect ratio; add `circle` keyword to force a circle; position with `at X% Y%`; supports the same color-stop and repeating-radial-gradient() features as linear.
- DESIGN TIP: dial down contrast for real projects — a jarring white-to-black or fully saturated gradient is for illustration only; production gradients usually blend between two close shades (e.g. two similar blues) for a subtle sense of depth the user may not consciously notice.
- `box-shadow: offsetX offsetY blurRadius spreadRadius color` — offsets of 0/0 puts the shadow directly behind the element; blur softens edges; positive spread enlarges the shadow, negative shrinks it; `inset` keyword moves the shadow inside the border instead of outside (good for a "pressed/depressed" button state). Multiple shadows can be comma-separated and layered (e.g. one tight inset ring + one larger offset inset shadow for a convincing pressed effect).
- `text-shadow: offsetX offsetY blurRadius color` — same idea for text, but no `inset` and no spread-radius option.
- Depth-effect button recipe: subtle top-to-bottom gradient + soft blurred box-shadow for the resting/skeuomorphic state; on `:active`, swap to `inset` shadows (removes the "lifted" look, adds a "pressed" look). If also removing the browser's default focus outline (`:focus { outline:none }`) ALWAYS replace it with a custom visible focus style — never remove focus indication outright, or keyboard users lose track of where they are.
- Flat design alternative: solid `background-color` (no gradient), only a faint semi-transparent shadow (e.g. `box-shadow: 0 0.2em 0.2em rgba(0,0,0,0.15)`), and simple darker-shade `:hover`/`:active` background-color swaps instead of shading tricks.
- "Modern hybrid" button trick: a crisp (zero-blur) `box-shadow` offset only vertically (e.g. `box-shadow: 0 0.4em #148`) mimics a thick colored bottom border that still respects `border-radius` (a real `border` wouldn't curve as cleanly with corners, and box-shadow can carry the curve where a flat border edge can't blend as well) — on `:active`, shift the element down with `transform: translateY(...)` AND shrink the shadow offset by the same amount, so the shadow doesn't move but the button visually "presses into" it.
- Multiple background images/gradients: `background-image: url(a.jpg), linear-gradient(...)` — first listed paints IN FRONT of later ones (like z-order); per-image `background-position`/`background-size`/`background-repeat` accept comma-separated per-layer values (a single value applies to all layers uniformly).
- `background-size: cover` (fills the box completely, may crop edges) vs `contain` (shows the whole image, may letterbox/leave gaps) — the two standard keyword choices beyond explicit px/% sizing.
- `background-blend-mode` blends MULTIPLE BACKGROUNDS (images/gradients/color) of the SAME element; `mix-blend-mode` blends an element's own rendered content (its box, text, borders) with whatever is stacked BEHIND it (its container's background, siblings) — different property depending on whether you're combining multiple backgrounds on one thing, or one element visually against another.
- Blend-mode categories & names: Darken (multiply, darken, color-burn), Lighten (screen, lighten, color-dodge), Contrast (overlay, hard-light, soft-light — increase contrast, useful for texture overlays; darker source textures often pair better with soft-light, lighter textures with hard-light/overlay, front/back order matters and can reverse this), Composite (hue, saturation, luminosity, color — apply one HSL-ish channel from front layer onto back layer; luminosity/color are inverses of each other depending on which layer is "front"), Comparative (difference, exclusion).
- Practical blend-mode uses: tint a photo with a single brand hue (background-color behind image + `background-blend-mode: luminosity`), add fake film-grain/canvas texture (tile a small grayscale texture image over the photo with `soft-light`/`hard-light`/`overlay`), knock text out of a colored banner so the image behind shows through it (mid-gray text/background + `mix-blend-mode: hard-light` — contrast blend modes have little visible effect on true middle-gray, letting whatever's behind bleed through the "cut-out" look).
- Browser support caveat (as of writing): most blend modes unsupported in IE/Edge, composite blend modes (hue/saturation/luminosity/color) also unsupported in Safari — wrap in `@supports` feature queries with a plain fallback background when it matters.

- CONTRAST IS THE MECHANISM OF VISUAL HIERARCHY: contrast only works against an established pattern — consistent spacing/sizing/color everywhere else is what makes the ONE exception draw the eye. This is a strong argument for modular CSS/pattern libraries (ch9-10): reusing the same Button/Tile module everywhere creates the very consistency that then lets one CTA variant stand out.
- Three main levers for contrast: color (a single dark/bright item among light ones), whitespace (space around an item isolates and elevates it), and size (a large element among smaller ones). Combine multiple levers for the strongest effect (e.g. a hero CTA: bigger text + lots of white space + a solid contrasting button color).
- Contrast also works in reverse — deliberately LOW contrast (small font, gray-on-light-gray) tells the user "this is unimportant," e.g. a footer. Every page should have one clear primary purpose/action; the designer's (and your) job is to make that stand out and let everything else recede.
- Store every palette color as a custom property (or preprocessor variable) even when using CSS custom properties requires modern-browser support — a mid-project brand-color change becomes a one-line edit instead of a site-wide find/replace.
- Convert palette colors to HSL to understand their relationships: HSL exposes patterns hex/RGB hide — e.g. discovering that all "brand green" shades share the exact same hue number and differ only in lightness makes it trivial to derive a new consistent shade (same hue, tweak saturation/lightness) rather than guessing at a new hex value. Also reveals that "pure" grays in a real palette are rarely 0% saturation — a slight saturation tint (sharing the site's hue) makes grays feel richer/less flat than a truly neutral gray.
- Browser DevTools trick: shift-click a color swatch in the Styles panel to cycle hex → rgb() → hsl() display for any property value (not custom properties in Firefox) — fast way to convert without an external tool.
- Naming multi-shade palette variables: prefer a numeric/scalar naming scheme (e.g. `--gray-50`, `--gray-80`, roughly tracking lightness) over descriptive names (`--light-gray`, `--extra-light-gray`) — descriptive names run out of room when you inevitably need one more shade between two existing ones.
- Deriving a NEW color that harmonizes with an existing palette: find the HSL complement by adding/subtracting 180 from the hue (e.g. hue 162 green → hue 342 red-magenta for an "active/error" accent), then reuse (or slightly desaturate) the existing saturation/lightness values from the palette rather than inventing a brand-new intensity — keeps the new color visually consistent with the rest of the site rather than "louder" than everything else.
- ACCESSIBILITY — TEXT CONTRAST: never use pure black-on-white (#000/#fff) for body copy — the extreme contrast causes eye fatigue on backlit screens; use a dark gray (e.g. HSL lightness ~15%) on off-white instead, keeping the *impression* of black-on-white while easing strain. But don't go too far the other way either (light-gray-on-light-gray) — WCAG defines minimum contrast RATIOS: Level AA = 4.5:1 normal text / 3:1 large text (≥24px regular or ≥18.67px bold); Level AAA = 7:1 normal / 4.5:1 large. Use an online contrast-ratio checker rather than computing the WCAG formula by hand. Aim for AAA on primary body copy where practical; AA is an acceptable bar for secondary/decorative text. Thin font weights (300, 100) reduce PERCEIVED contrast even at an identical passing color-contrast ratio — compensate with a stronger color contrast when using thin/light font weights.
- SPACING PRECISION — px vs relative units: designer mockups are typically specified in px; converting each spec value to em/rem (divide desired px by the base font size, e.g. 10/16=0.625em) costs more upfront work but keeps the whole layout scaling proportionally if you later adopt a responsive/fluid base font size — discuss this tradeoff with the designer if precision at fixed sizes matters to them.
- Padding vs margin choice when matching a mockup: use PADDING when the space needs to visually belong to a container that has its own background/color (e.g. vertical space inside a colored navbar, so the color extends to fill it); use MARGIN for space between siblings/outside elements with no shared background need.
- LINE-HEIGHT AND VERTICAL SPACING (a frequent px-matching gotcha): a text element's rendered box is taller than its glyphs alone — the extra `(line-height − 1) × font-size` space splits evenly above and below the actual character glyphs. So a literal 30px margin between a heading and paragraph will visually render as MORE than 30px, because each element already contributes some of that "line-height air" on its own edge. Fix: compute the actual extra line-height space each element contributes and SUBTRACT it from the margin you set so the perceived gap matches the spec exactly (e.g. wanting a visual 30px gap between two lines at line-height 1.4 / 16px font requires roughly a 24px margin, not 30px, because each side already contributes ~3px of line-height padding). For a large-font element (e.g. a hero headline) redo this same subtraction using ITS OWN font-size × line-height, not the base 16px.
- Base paragraph margins (top+bottom) applied once in base/global styles, plus margin-collapsing (ch3), let a heading's bottom margin and the following paragraph's top margin combine into a single correctly-sized gap automatically, rather than needing one-off overrides everywhere.
- INLINE ELEMENT SPACING GOTCHA (tag/chip lists): giving `display:inline` items padding makes each individual chip look padded, but padding on an inline element does NOT increase the height of the LINE BOX itself (only line-height does) — so if the chips wrap onto a second row, their padded backgrounds visually overlap the row above/below. Fix: give the inline items a generously large `line-height` (not padding) to create the needed vertical room between wrapped rows. Alternative: use flexbox or inline-block instead of `inline` — those DO grow the line to fit their own padding — at the cost of losing the free "natural whitespace becomes gutter" behavor of true inline elements and losing the ability for a single item's inner text to line-wrap independently (inline-block/flex items wrap as a whole unit, not mid-text).

- Choosing a typeface pairing changes a page's whole tone (formal/serif vs. informal/sans vs. playful) — pick fonts deliberately for the feel you want, not just legibility.
- Common web-font providers: Google Fonts (free, huge open-source library — good default recommendation), Typekit, Webtype. They handle hosting/licensing for you; using one is usually preferable to hand-rolling @font-face unless you need a specific font not on any service.
- LIMIT the number of font weights/styles you load — each additional weight is another network request/file and slows page load; only select the exact weights you actually use (e.g. one light weight for body, one bold weight for headings), don't grab "regular + bold + italic + light + ..." just in case.
- `@font-face` mechanics: each distinct (font-family, font-style, font-weight) combination needs its OWN `@font-face` rule; `src:` lists fallbacks in preference order — `local('Font Name')` first (use an already-installed system copy if present, skip the download), then `url(...) format('woff2')`, then a `url(...) format('woff')` fallback for older browsers (WOFF2 compresses better/loads faster but isn't universal — always provide both when self-hosting). If a page requests a weight/style with no matching @font-face, the browser approximates by geometrically distorting the closest available weight — never looks as good as a real font file; don't rely on synthetic bold/italic.
- Typeface (a family, e.g. "Roboto") vs. font (one specific weight/style variant within that family, e.g. "Roboto Light") — distinct terms worth using correctly.
- `line-height` and `letter-spacing` are the two most commonly neglected typography properties, yet tuning them meaningfully improves both aesthetics and reading comfort:
  - Initial line-height (`normal`, ≈1.2, encoded per font) is usually too tight for body copy — aim for roughly 1.4–1.6 for paragraph/body text. Longer line lengths need a taller line-height (helps the eye track back to the correct next line); classic print-design guidance: aim for ~45–75 characters per line for best readability.
  - `letter-spacing` (aka "tracking" in design terms) should be a small value — start experimenting in ~0.01em increments; overdoing it draws unwanted attention to the spacing itself rather than the words.
  - Headings/short text can tolerate more creative spacing than body copy: negative letter-spacing (e.g. -0.02em) to tighten a large display headline, or wider positive spacing paired with `text-transform: uppercase` for small caps-style buttons/nav links (all-caps text generally looks better with MORE letter-spacing, not less).
  - Always re-check heading spacing with an artificially long/wrapped heading, not just the short one from the mockup — line-height that looks right on one line can look wrong once a heading wraps to two.
  - `text-transform: uppercase/lowercase/capitalize` should do stylistic capitalization in CSS, never by retyping the HTML content in caps — keeps a single point of change if the design changes, and preserves grammatically-correct source text (still hand-capitalize genuine proper nouns/acronyms in the HTML itself).
  - Converting a designer's leading/tracking specs to CSS: leading (in pt) → px via ×1.333 (96px/in ÷ 72pt/in), then ÷ font-size for a unitless line-height; tracking (usually given in thousandths of an em) → letter-spacing by ÷1000 to get an em value.
  - "Vertical rhythm" (advanced/optional): aligning all text baselines site-wide to one repeating baseline grid for extra visual polish — powerful but requires switching to unit-based (not unitless) line-heights, which changes inheritance behavior (ch2) — remember to re-declare line-height explicitly anywhere the font-size changes if you go this route.
- FOUT vs FOIT — the web-font-loading tradeoff: browsers either render with a fallback font immediately and swap to the web font once loaded (Flash of Unstyled Text — a visible layout jump when the fonts differ in size/metrics) or hide text entirely until the web font arrives (Flash of Invisible Text — no visible jump, but a blank page if the font is slow or fails). Neither is fully avoidable; the goal is mitigating whichever failure mode matters most for your users' likely connection speed.
- Practical mitigation pattern (pre-`font-display` era): use a JS font-loading-detection library (e.g. Font Face Observer) to add a `fonts-loaded` or `fonts-failed` class to `<html>` once loading resolves (with a timeout, e.g. 2000ms) — then use those classes in your CSS to control the FOIT/FOUT tradeoff explicitly: either (a) style with fallback fonts by default and only apply the web font under `.fonts-loaded` (FOIT → FOUT once ready), or (b) style with the web font by default and revert to a system-font fallback under `.fonts-failed` if loading times out or errors (keeps a hard-timeout FOIT bounded so it never hangs forever). Prefer approach (b) generally: don't let a failed/slow font download leave the page permanently blank.
- Modern equivalent: the `font-display` CSS descriptor inside `@font-face` (no JS needed) — `auto` (browser default, usually FOIT), `swap` (fallback shown immediately, swapped when ready — a FOUT), `fallback` (brief ~100ms invisible period, then fallback if not ready, swaps in later if it eventually loads — bounded FOIT), `optional` (like fallback, but the browser may skip the web font entirely on a slow connection and never swap it in) — `fallback` suits fast connections, `swap` suits typically-slow audiences, `optional` suits a "nice-to-have" decorative font that isn't essential to read the content.
- If matching fallback-font spacing to the eventual web font, use a font-style-matcher tool (adjust the fallback's own line-height/letter-spacing/size to approximate the web font's metrics) so any FOUT layout shift is as small/unnoticeable as possible.
- DevTools throttling tip: use the Network tab's throttle preset (e.g. "Regular 3G") plus "Disable cache" to realistically test font-loading (and general page-load) behavior on a slow connection instead of only your fast dev machine — remember to turn it back off afterward.
